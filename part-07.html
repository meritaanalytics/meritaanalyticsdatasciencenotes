Part 7

Exploratory Data Analysis

EDA is the habit of looking at data carefully before you model it or report it. This Part gives you a repeatable recipe: ask the question first, check structure and quality, describe one column, then pairs of columns, then segments, outliers and time. You apply it to real penguin measurements and to a synthetic lender database, wrap it in a reusable `eda_report()` function and finish with a template for writing findings.

In this part
  • Follow a ten-step EDA recipe from question to findings
  • Check a table's structure and quality before trusting any number
  • Describe single columns, pairs of columns and segments, with group sizes
  • Find, investigate and decide about outliers and time patterns
  • Turn patterns into hypotheses and write findings with numbers
You need first Part 4 and Part 5Time 4 to 5 hours

#7.1 What EDA is and the recipe we follow

Exploratory Data Analysis (EDA) is a structured first look at a dataset: what does it contain, can you trust it, and which patterns deserve a closer test? It proves nothing. It produces questions you can defend and problems you must fix before any model or dashboard. Most wrong analyses are not wrong maths; they are a misread column, a hidden duplicate, or groups that were never comparable.

Step Question it answers Typical tools
1. Question What decision is this for? one written sentence
2. Structure What is one row? Which columns and types? shape, dtypes, head
3. Quality Missing, duplicate, impossible, censored? isna, duplicated, range checks
4. Univariate How is each column distributed? describe, value_counts, histogram
5. Bivariate How do two columns relate? corr, groupby, crosstab, scatter
6. Segments Do groups differ, and are they big enough? groupby with counts and rates
7. Outliers Which values are extreme, and why? IQR fence, z-score
8. Time What trends and seasons exist? resample, same-month comparison
9. Hypotheses What do we believe, and how sure are we? chi-square, rank tests
10. Findings What do we tell the reader? a findings template (7.11)

Rule. Write the question before you open the data. 'Explore the table' is a task. 'Which loan products and borrower profiles go bad most often, so we can tighten approval rules?' is a question: it tells you which columns matter and when to stop.

We use two datasets. The first is the Palmer penguins table (real, CC0 licence): 344 penguins of three species measured on three islands. The second is a synthetic lender database (1,000 customers, 20,000 transactions, a few hundred loans), which gives us credit-risk questions that public data cannot. Our running questions: how do the penguin species differ? and where is the credit risk in the lender's loans?

Rule. Always write down the grain. A default rate per loan and a default rate per customer are different numbers, and mixing them is a classic reporting error. If you count customers, use nunique, not len.

#7.3 Data quality: missing, duplicate, impossible and censored

A quality check is a list of tests that can fail: completeness (missing values), uniqueness (duplicates), validity (values in allowed ranges), consistency (two columns that must agree) and timeliness (does the data cover the period you think). Part 4 taught the cleaning verbs; here we measure the problems.

def quality_table(df):
    '''One row per column: dtype, missing count, missing percent, distinct values.'''
    return pd.DataFrame({"dtype": df.dtypes.astype(str), "missing": df.isna().sum(),
                         "missing_pct": (df.isna().mean() * 100).round(1), "distinct": df.nunique()})

print(quality_table(peng).to_string())

#Censoring: a quality problem hidden in a good column

Right-censoring means the outcome has not had time to happen yet. A loan disbursed last month cannot have defaulted, so counting it as 'good' flatters the default rate. Look at how loan status differs by product.

print(pd.crosstab(loans["product"], loans["status"]))
print("latest disbursement:", loans["disbursement_date"].max().date())

status          Active  Closed  Defaulted
product                                  
Asset Finance       37       1         19
Digital Loan         0     198         25
SME Loan            49      39         28
Salary Advance       0     126         38
latest disbursement: 2025-09-30

Some products have many loans still Active, others have none. A raw 'defaulted divided by all loans' rate would compare products at different stages of life. In 7.6 we use a fairer denominator: loans whose outcome is known.

Common mistake. Dropping every row with a missing value 'to be safe'. If the missing rows differ from the rest you have removed exactly the cases you wanted to study.

#7.6 Segment comparison: rates, denominators and sample size

Most business EDA ends up comparing segments: product, county, channel, species. Three rules keep it honest: (1) define the rate with a fair denominator, (2) show the group size, (3) give a rough uncertainty so a small group is not over-read. First the penguins: always keep the count beside the summary.

                                  median_flipper=("flipper_length_mm", "median")).round(0)

Now a credit-risk rate. We use settled loans (Closed plus Defaulted) as the denominator, and a Wilson 95% interval, a standard range for a proportion, to show how much a small group can move.

def wilson(k, n, z=1.96):
    '''95% Wilson interval for k out of n; returns (low, high) as fractions.'''
    if n == 0:
        return (np.nan, np.nan)
    p = k / n
    centre = (p + z**2 / (2 * n)) / (1 + z**2 / n)
    half = z * np.sqrt(p * (1 - p) / n + z**2 / (4 * n**2)) / (1 + z**2 / n)
    return (centre - half, centre + half)

settled = loans[loans["status"].isin(["Closed", "Defaulted"])].copy()
settled["defaulted"] = (settled["status"] == "Defaulted").astype(int)
by_prod = settled.groupby("product")["defaulted"].agg(n="count", defaults="sum")
by_prod["rate_pct"] = (by_prod["defaults"] / by_prod["n"] * 100).round(1)
ci = [wilson(k, n) for k, n in zip(by_prod["defaults"], by_prod["n"])]
by_prod["ci_low"] = [round(a * 100, 1) for a, b in ci]
by_prod["ci_high"] = [round(b * 100, 1) for a, b in ci]
naive = loans.groupby("product")["status"].apply(lambda s: (s == "Defaulted").mean() * 100).round(1)
by_prod["naive_pct"] = naive
print(by_prod.sort_values("rate_pct", ascending=False).to_string())

Where two products' intervals overlap heavily, the data cannot separate them yet. A very high rate that rests on few settled loans is a lead, not a conclusion. The naive_pct column divides by all loans including those still active, so it understates risk for products with many active loans. Settled-only rates can overstate risk for long products whose good loans have not finished; credit teams build vintage curves to remove this problem.

A group difference can shrink once you split by a second variable. Credit score is the usual suspect: bin it and compare again.

#7.7 Outliers: find them, understand them, then decide

An outlier is a value far from the rest. It may be a data error (an extra zero), a rare real event (a large SME loan) or the most interesting row in the table (fraud). The rule is detect, investigate, decide; never delete automatically. Two detectors: the IQR fence (Q1 minus 1.5 x IQR, Q3 plus 1.5 x IQR) and the z-score (how many standard deviations from the mean).

def iqr_fence(s, k=1.5):
    '''Return (low, high) fence values: Q1 - k*IQR and Q3 + k*IQR.'''
    q1, q3 = s.quantile([0.25, 0.75])
    iqr = q3 - q1
    return q1 - k * iqr, q3 + k * iqr

mass = peng["body_mass_g"].dropna()
lo, hi = iqr_fence(mass)
print(f"penguin body mass fence: {lo:,.0f} to {hi:,.0f} g | flagged: {int(((mass < lo) | (mass > hi)).sum())}")

plo, phi = iqr_fence(loans["principal_ksh"])
big = loans[loans["principal_ksh"] > phi]
print(f"loan principal fence high: Ksh {phi:,.0f} | flagged: {len(big)}")
print(big["product"].value_counts().to_dict())

penguin body mass fence: 1,750 to 6,550 g | flagged: 0
loan principal fence high: Ksh 445,350 | flagged: 59
{'Asset Finance': 41, 'SME Loan': 18}

No penguin is flagged, so there is nothing to investigate. The flagged loans all belong to the products with the largest tickets: they are large for the whole table but typical for their product. Outlier rules applied to a whole table often just rediscover that groups differ, so apply the fence within each group.

ok = txns[txns["status"] == "Success"].copy()

print("flagged by one overall fence:", int(ok["high_overall"].sum()),

print(ok.groupby("txn_type")[["high_overall", "high_in_type"]].sum().to_string())

Common mistake. Removing outliers until the chart looks nice. If a decision depends on the removal, say so and show the result both ways.

#7.8 Time trends: level, seasonality and rates

Time adds three questions: is there a trend (slow rise or fall), seasonality (a repeating pattern by month or weekday), and breaks (a sudden jump)? Rule. Compare like with like: the same month in another year, rates rather than counts, and complete periods (a half-finished month always looks like a collapse).

#7.9 From patterns to hypotheses: is it real or noise? (Advanced)

An EDA pattern is a hypothesis, not a result. 'Mass-segment customers default more often' is a claim you can state, test and disprove. A screening test asks: if the groups were really the same, how often would chance alone produce a gap this large? That probability is the p-value (Part 8 explains it properly). For two categorical columns the usual screen is the chi-square test of independence.

from scipy import stats

sg = loans.merge(customers[["customer_id", "segment"]], on="customer_id")
sg = sg[sg["status"].isin(["Closed", "Defaulted"])]
table = pd.crosstab(sg["segment"], sg["status"])
chi2, p_val, dof, _ = stats.chi2_contingency(table)
print(table.to_string())
print(f"chi-square = {chi2:.1f}, degrees of freedom = {dof}, p-value = {p_val:.2g}")

A very small p-value says the gap between segments is unlikely to be chance. It does not say income causes default: the segment may also differ in product mix or credit score. For a numeric column against a yes or no outcome, use a rank test, which does not assume a bell shape.

d = settled.groupby("defaulted")["credit_score"]

u, p_u = stats.mannwhitneyu(d.get_group(1), d.get_group(0))

Common mistake. Testing dozens of pairs and reporting the one with p below 0.05. With 20 comparisons you expect one 'significant' result by luck. Decide the few comparisons that matter before looking, or say how many you tried.

#7.10 A reusable eda_report() function

Once the routine is stable, wrap it in a function. A good eda_report does not replace thinking; it makes sure you never skip the first look. This version returns a dictionary of small tables (structure, numeric summary, categorical summary, strongest pairs, outlier counts, dates) and prints a short summary.

def eda_report(df, target=None, date_col=None, id_cols=(), max_levels=8, verbose=True):
    '''First-look EDA. Returns a dict of tables; prints a compact summary when verbose.'''
    out = {}
    out["structure"] = pd.DataFrame({"dtype": df.dtypes.astype(str), "missing": df.isna().sum(),
                                     "missing_pct": (df.isna().mean() * 100).round(1),
                                     "distinct": df.nunique()})
    num = [c for c in df.select_dtypes("number").columns if c not in id_cols]
    cat = [c for c in df.columns if c not in num and c != date_col and c not in id_cols
           and df[c].nunique() <= max_levels]
    if num:
        desc = df[num].describe(percentiles=[0.5]).T
        desc["skew"] = df[num].skew()
        q1, q3 = df[num].quantile(0.25), df[num].quantile(0.75)
        desc["above_fence"] = (df[num] > q3 + 1.5 * (q3 - q1)).sum()
        out["numeric"] = desc[["count", "mean", "50%", "std", "min", "max", "skew", "above_fence"]].round(2)
    out["categorical"] = {c: df[c].value_counts(dropna=False).head(max_levels) for c in cat}
    if len(num) > 1:
        cm = df[num].corr(method="spearman").abs()
        pairs = cm.where(np.triu(np.ones(cm.shape, dtype=bool), 1)).stack().sort_values(ascending=False)
        out["top_pairs"] = pairs.head(5).round(2)
    if target in num:
        out["target_by_cat"] = {c: df.groupby(c, observed=True)[target].agg(["count", "mean"]).round(3) for c in cat}
    if date_col:
        d = pd.to_datetime(df[date_col], errors="coerce")
        out["dates"] = {"min": d.min(), "max": d.max(), "unparseable": int(d.isna().sum())}
    out["duplicates"] = int(df.duplicated().sum())
    if verbose:
        print(f"rows={len(df):,} columns={df.shape[1]} duplicates={out['duplicates']} "
              f"cells missing={int(df.isna().sum().sum())}")
        print("numeric:", num, "\ncategorical:", cat)
    return out

#7.11 What to write in the findings: a template

Analysis that stays in your notebook helps nobody. The findings section turns EDA into something a manager can act on. Use the same structure every time so readers know where to look.

Block What goes in it Example
Question the decision the analysis supports Where is credit risk concentrated?
Data source, grain, period, rows synthetic loans, one row per loan
Quality what you checked, found, did no invalid values; some loans still Active
Key findings 3 to 5 sentences, each with a number and a denominator default rate by score band
Evidence a table or chart per finding band table, segment chart
Limits censoring, small groups, correlation not cause synthetic data
Recommendations action, owner, how to measure it review approval at low scores
Next steps tests or data you would add vintage curves, a scorecard model

A good finding follows claim, number, comparison, so-what. 'Low scores default more' is a topic; a finding says how much more, on how many loans, and what to do. Fill the template from code so numbers cannot drift from the data.

The sentences contain the number, the group size and a warning where the group is small. They never use 'significant' unless a test supports it.

Checklist. Before you share any EDA: (1) the question is written; (2) grain and period are stated; (3) quality checks and counts are shown; (4) every rate has a denominator; (5) outliers were investigated, not silently removed; (6) seasonality was considered; (7) claims say 'in this data'; (8) there is a limits line and a next step.

Key takeaways
  • Write the question first; EDA without a question produces dozens of charts and no point.
  • State the grain of the table, then measure quality: missing, duplicates, validity, consistency, censoring.
  • Describe one column, then pairs, then segments, always showing the group size next to every rate.
  • Detect, investigate, then decide about outliers; never delete them just to tidy a chart.
  • Compare like with like over time, and treat every pattern as a hypothesis, not a result.
  • Write findings as claim, number, comparison, so-what, and list the limits of the data.
