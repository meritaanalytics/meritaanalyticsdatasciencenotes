#6.1 What a database is: tables, rows, columns and keys

A database is an organised store of data. A relational database keeps it in tables, like spreadsheets with strict rules: each row is one record (one customer) and each column is one attribute (the county). Tables are linked by keys. A primary key identifies a row (customers.customer_id). A foreign key holds another table's primary key (loans.customer_id points to customers.customer_id). SQL (Structured Query Language) is the language you use to ask questions of those tables.

Why learn it? Company data lives in databases. Asking for only the rows and columns you need is faster and safer than exporting everything to Excel. We use SQLite, which is built into Python, and a synthetic lender database made in code with fixed seeds (customers, transactions, loans, repayments). No row describes a real person or lender, so every finding describes this synthetic data only.

#6.3 Aggregates, GROUP BY and HAVING

An aggregate collapses many rows into one number: COUNT, SUM, AVG, MIN, MAX. GROUP BY computes it once per group. WHERE filters rows before grouping; HAVING filters groups after.

WHERE status = 'Success'

#6.4 JOINs: combining tables

A join matches rows of two tables on a key. INNER JOIN keeps only matching rows. LEFT JOIN keeps every row of the left table and fills NULL where the right side has no match.

INNER JOIN matches only loans with their customer details
LEFT JOIN all left rows all customers, even without a loan
LEFT JOIN ... WHERE r.key IS NULL left rows with no match customers who never borrowed

#The join-inflation trap

The most common wrong number in analytics. A customer has many transactions and many loans. Join both to the customer table and each loan row repeats once per transaction, so loan totals inflate. The cure: aggregate the many-side to one row per key first, then join.

wrong = q('''SELECT SUM(l.principal_ksh) AS s FROM customers c
             JOIN loans l ON l.customer_id = c.customer_id
             JOIN transactions t ON t.customer_id = c.customer_id''').iloc[0, 0]
truth = q("SELECT SUM(principal_ksh) FROM loans").iloc[0, 0]
print(f"inflated: Ksh {wrong:,.0f}")
print(f"correct : Ksh {truth:,.0f}")
print("inflation factor:", round(wrong / truth, 1), "x")

inflated: Ksh 1,707,649,100
correct : Ksh 83,414,000
inflation factor: 20.5 x

Check. After every join, compare row counts and key totals before and after. If the left table grows, the right key is not unique. In Pandas the same guard is merge(..., validate="many_to_one").

#6.5 CASE WHEN: if/else inside a query

CASE WHEN builds a new value row by row. It is also the engine of conditional aggregation: count or sum only the rows that meet a condition.

q('''
SELECT customer_id, monthly_income_ksh,
       CASE WHEN monthly_income_ksh < 25000 THEN 'Low'
            WHEN monthly_income_ksh < 70000 THEN 'Middle'
            ELSE 'High' END AS income_band
FROM customers
LIMIT 5
''')
customer_id monthly_income_ksh income_band
0 C0001 58800 Middle
1 C0002 143200 High
2 C0003 65400 Middle
3 C0004 19500 Low
4 C0005 14800 Low 
q('''
SELECT product,
       COUNT(*) AS loans,
       SUM(CASE WHEN status = 'Defaulted' THEN 1 ELSE 0 END)        AS defaulted,
       SUM(CASE WHEN days_past_due BETWEEN 1 AND 30 THEN 1 ELSE 0 END) AS dpd_1_30,
       SUM(CASE WHEN days_past_due > 30 THEN 1 ELSE 0 END)          AS dpd_over_30
FROM loans GROUP BY product ORDER BY loans DESC
''')
product loans defaulted dpd_1_30 dpd_over_30
0 Digital Loan 223 25 0 25
1 Salary Advance 164 38 0 38
2 SME Loan 116 28 4 33
3 Asset Finance 57 19 6 21

#6.6 Subqueries and CTEs

A subquery is a SELECT inside another statement. A scalar subquery returns one value, so it can sit in WHERE like a constant. A CTE (common table expression, WITH name AS (...)) gives a step a name so a long query reads top to bottom like a recipe. Prefer CTEs once a query has more than one step.

q('''
SELECT loan_id, product, principal_ksh
FROM loans
WHERE principal_ksh > (SELECT AVG(principal_ksh) FROM loans)
ORDER BY principal_ksh DESC
LIMIT 4
''')
loan_id product principal_ksh
0 L0093 Asset Finance 2301800.0
1 L0422 Asset Finance 2038500.0
2 L0321 Asset Finance 1596300.0
3 L0462 Asset Finance 1414400.0

The inner query returns the average loan; the outer query keeps loans above it.

q('''
WITH per_product AS (
    SELECT product, COUNT(*) AS loans, SUM(status = 'Defaulted') AS defaults
    FROM loans GROUP BY product
),
overall AS (
    SELECT SUM(defaults) * 1.0 / SUM(loans) AS portfolio_rate FROM per_product
)
SELECT p.product, p.loans, p.defaults,
       ROUND(100.0 * p.defaults / p.loans, 2) AS default_rate_pct,
       ROUND(100.0 * o.portfolio_rate, 2)     AS portfolio_pct
FROM per_product p CROSS JOIN overall o
ORDER BY default_rate_pct DESC
''')
product loans defaults default_rate_pct portfolio_pct
0 Asset Finance 57 19 33.33 19.64
1 SME Loan 116 28 24.14 19.64
2 Salary Advance 164 38 23.17 19.64
3 Digital Loan 223 25 11.21 19.64

Step 1 summarises each product, step 2 finds the portfolio rate. In SQLite status = 'Defaulted' is 1 or 0, so SUM counts matches.

Rule. A CTE is a named, temporary result for one statement. Run each step alone to debug. If several queries need the same logic, save it as a view (6.9).

#6.7 Window functions

A window function computes a value for each row using a set of related rows without collapsing them, unlike GROUP BY. The shape is function() OVER (PARTITION BY group ORDER BY sort). PARTITION BY splits rows into groups; ORDER BY orders them inside each group.

#ROW_NUMBER: top N per group

The classic interview question: the three largest loans in each product. Number the rows in a CTE, then filter in the outer query (a window result cannot be used in the same WHERE).

top3 = q('''
WITH ranked AS (
    SELECT product, loan_id, principal_ksh,
           ROW_NUMBER() OVER (PARTITION BY product ORDER BY principal_ksh DESC) AS rn
    FROM loans
)
SELECT * FROM ranked WHERE rn <= 3 ORDER BY product, rn
''')
print(len(top3), "rows =", top3["product"].nunique(), "products x 3")
top3.head(6)

#RANK and DENSE_RANK with ties

When values tie, ROW_NUMBER never repeats, RANK repeats and then skips a number, DENSE_RANK repeats without skipping. Credit scores are whole numbers, so ties are common.

q('''
SELECT credit_score,
       ROW_NUMBER() OVER (ORDER BY credit_score DESC) AS row_number,
       RANK()       OVER (ORDER BY credit_score DESC) AS rank,
       DENSE_RANK() OVER (ORDER BY credit_score DESC) AS dense_rank
FROM loans ORDER BY credit_score DESC LIMIT 6
''')

#Running totals and moving averages

Add ORDER BY inside OVER and SUM becomes a running total. A frame such as ROWS BETWEEN 2 PRECEDING AND CURRENT ROW gives a 3-month moving average.

tr = q('''
SELECT month, txn_count,
       SUM(txn_count) OVER (ORDER BY month) AS running_txns,
       ROUND(AVG(txn_count) OVER (ORDER BY month
             ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 1) AS ma3_txns
FROM vw_monthly_kpis ORDER BY month
''')
print(tr.head(4).to_string(index=False))
n_all = q("SELECT COUNT(*) FROM transactions").iloc[0, 0]
print("final running total equals all rows:", bool(tr["running_txns"].iloc[-1] == n_all))

  month  txn_count  running_txns  ma3_txns
2024-01        728           728     728.0
2024-02        711          1439     719.5
2024-03        833          2272     757.3
2024-04        778          3050     774.0

Pattern. Share of total in one pass: 100.0 * x / SUM(x) OVER (). An empty OVER () means one window over the whole result.

Common mistake. Putting a window function in WHERE (it fails), or forgetting PARTITION BY so the ranking runs across the whole table.

#6.8 Dates in SQLite

SQLite has no true date type. Dates are stored as ISO text YYYY-MM-DD, which sorts correctly as plain text. The functions date(), julianday() and strftime(format, value) read them. strftime is the workhorse for monthly reports.

strftime code Gives For 2025-03-14
%Y 4-digit year 2025
%m month 01-12 03
%Y-%m year-month 2025-03
%w weekday, 0 = Sunday 5 
q('''
SELECT strftime('%Y-%m', txn_date) AS month, COUNT(*) AS txns,
       ROUND(SUM(amount_ksh), 0) AS value_ksh
FROM transactions
WHERE txn_date >= '2025-10-01'
GROUP BY month ORDER BY month
''')
month txns value_ksh

1 2025-11 793 2690179.0

Use a half-open range (>= start, < end) to filter dates; it stays fast and avoids wrapping the column in a function.

#The DATE_FORMAT dialect difference

MySQL users write DATE_FORMAT(d, '%Y-%m'). SQLite has no such function, so a copied query fails. The SQLite spelling is strftime('%Y-%m', d): the format comes first, then the date. The ideas port between databases; only the function names change, so keep the vendor's date-function page open when you move.

#6.9 Views and NULL handling

A view is a saved SELECT with a name. It stores no data; each time you query it, the database reruns the saved query. Views give a whole team one definition of a metric such as "active customer", so reports do not disagree.

con.execute("DROP VIEW IF EXISTS p06_county_summary")
con.execute('''
CREATE VIEW p06_county_summary AS
SELECT c.county, COUNT(DISTINCT c.customer_id) AS customers,
       COUNT(l.loan_id) AS loans, ROUND(AVG(l.credit_score), 0) AS avg_score
FROM customers c LEFT JOIN loans l ON l.customer_id = c.customer_id
GROUP BY c.county
''')
con.commit()
q("SELECT * FROM p06_county_summary ORDER BY customers DESC LIMIT 4")
county customers loans avg_score
0 Nairobi 354 191 599.0
1 Mombasa 123 60 590.0
2 Kiambu 102 54 594.0
3 Nakuru 100 64 603.0

A view is queried like a table. The built-in views vw_monthly_kpis and vw_loan_portfolio work the same way.

#NULL: missing is not zero

NULL means unknown. Any comparison with NULL, even NULL = NULL, is unknown, and WHERE keeps only rows that are true. So = NULL finds nothing; write IS NULL or IS NOT NULL. In repayments, an unpaid instalment has a NULL paid_date. COUNT(column) skips NULLs, while COUNT(*) counts rows.

print("= NULL   :", q("SELECT COUNT(*) FROM repayments WHERE paid_date = NULL").iloc[0, 0])
print("IS NULL  :", q("SELECT COUNT(*) FROM repayments WHERE paid_date IS NULL").iloc[0, 0])
q('''SELECT COUNT(*) AS all_rows, COUNT(paid_date) AS with_paid_date,
            COUNT(*) - COUNT(paid_date) AS unpaid FROM repayments''')

= NULL   : 0
IS NULL  : 442
all_rows with_paid_date unpaid
0 2867 2425 442

COALESCE(a, b, ...) returns the first non-NULL value, and NULLIF(a, b) returns NULL when the two are equal, which guards against dividing by zero.

q('''
SELECT repay_id, due_date,
       COALESCE(paid_date, 'UNPAID')                         AS paid_or_flag,
       ROUND(amount_paid_ksh / NULLIF(amount_due_ksh, 0), 2) AS paid_ratio
FROM repayments WHERE paid_date IS NULL LIMIT 3
''')

Trap. NOT IN with a NULL in the list returns no rows at all. Prefer NOT EXISTS or the LEFT JOIN anti-join (6.4) when the column can be NULL.

#6.11 (Advanced) Credit-risk SQL: PAR, default rates and vintages

A lender asks three questions. How much of the book is late (portfolio at risk, PAR)? How many loans end in default (default rate)? How does each month's or quarter's lending (vintage) perform as it ages? All three are plain SQL. The definitions here are teaching versions on synthetic data; real lenders follow their own policy and regulator rules.

#Portfolio at risk (PAR30)

PAR30 is the share of the outstanding book with a payment more than 30 days overdue (days_past_due > 30). The database has no balance column, so we use the principal of loans that are not Closed as a proxy for the book. That overstates exposure on part-repaid loans, so state the definition next to the number.

par = q('''
SELECT product,
       SUM(principal_ksh)                                              AS book_ksh,
       SUM(CASE WHEN days_past_due > 30 THEN principal_ksh ELSE 0 END) AS par30_ksh,
       SUM(CASE WHEN days_past_due > 90 THEN principal_ksh ELSE 0 END) AS par90_ksh
FROM loans WHERE status != 'Closed' GROUP BY product
''')
par["PAR30_%"] = (100 * par["par30_ksh"] / par["book_ksh"]).round(1)
par["PAR90_%"] = (100 * par["par90_ksh"] / par["book_ksh"]).round(1)
print(par[["product", "book_ksh", "PAR30_%", "PAR90_%"]].to_string(index=False))
tot = par[["book_ksh", "par30_ksh"]].sum()
print(f"portfolio PAR30: {100 * tot['par30_ksh'] / tot['book_ksh']:.1f}%")

#Default rate by product, and right-censoring

Right-censoring means recent loans have been watched for only a short time, so many have had no chance to default yet. Dividing all defaults by all loans mixes fully observed old loans with barely observed young ones, which usually makes the rate look better than the truth. Compare with a seasoned group: loans at least 120 days old at the data cut-off (2025-12-31).

dr = q('''
WITH l AS (
    SELECT product, status,
           julianday('2025-12-31') - julianday(disbursement_date) AS age_days
    FROM loans
)
SELECT product, COUNT(*) AS all_loans,
       ROUND(100.0 * AVG(status = 'Defaulted'), 1)  AS naive_rate_pct,
       SUM(age_days >= 120)                         AS seasoned_loans,
       ROUND(100.0 * SUM(status = 'Defaulted' AND age_days >= 120)
             / SUM(age_days >= 120), 1)             AS seasoned_rate_pct
FROM l GROUP BY product ORDER BY seasoned_rate_pct DESC
''')

#Vintage curves

A vintage groups loans by the quarter they were disbursed. A vintage curve shows the cumulative default rate by months on book (MOB), so a 2024-Q1 loan at month 6 is compared fairly with a 2025-Q1 loan at month 6. The database stores days past due, not a default date, so we estimate the default date as the day the loan crossed 90 days past due. A vintage is reported at a given MOB only if its youngest loan is at least that old (MIN(age_mob) >= k): that is the censoring correction. We build the repeated SQL pieces in Python.

ks = [3, 6, 9, 12]
pieces = [f"CASE WHEN MIN(age_mob) >= {k} THEN "
          f"ROUND(100.0 * SUM(default_mob <= {k}) / COUNT(*), 1) END AS mob{k}_pct" for k in ks]
sql = '''
WITH base AS (
    SELECT strftime('%Y', disbursement_date) || '-Q' ||
           ((CAST(strftime('%m', disbursement_date) AS INTEGER) + 2) / 3)   AS vintage,
           (julianday('2025-12-31') - julianday(disbursement_date)) / 30.0  AS age_mob,
           CASE WHEN status = 'Defaulted'
                THEN (julianday('2025-12-31') - days_past_due + 90
                      - julianday(disbursement_date)) / 30.0 END            AS default_mob
    FROM loans
)
SELECT vintage, COUNT(*) AS loans, ''' + ", ".join(pieces) + '''
FROM base GROUP BY vintage ORDER BY vintage
'''
vint = q(sql)

#6.12 (Advanced) Indexes and EXPLAIN QUERY PLAN

An index is a sorted lookup structure on a column, like a book's index. It speeds up WHERE, JOIN and ORDER BY on that column but uses disk space and slows writes. EXPLAIN QUERY PLAN shows whether SQLite will SCAN the whole table (slow on big data) or SEARCH using an index (fast).

def plan(sql):
    '''Return the query-plan lines as a list of strings.'''
    return q("EXPLAIN QUERY PLAN " + sql)["detail"].tolist()

look = "SELECT * FROM transactions WHERE txn_date = '2025-06-30'"
print("before:", plan(look))
con.execute("CREATE INDEX IF NOT EXISTS p06_idx_txn_date ON transactions(txn_date)")
print("after :", plan(look))

before: ['SCAN transactions']
after : ['SEARCH transactions USING INDEX p06_idx_txn_date (txn_date=?)']
fn_sql = "SELECT * FROM transactions WHERE strftime('%Y', txn_date) = '2025'"
rng_sql = "SELECT * FROM transactions WHERE txn_date >= '2025-01-01' AND txn_date < '2026-01-01'"
print("function on column:", plan(fn_sql))
print("half-open range   :", plan(rng_sql))

function on column: ['SCAN transactions']
half-open range   : ['SEARCH transactions USING INDEX p06_idx_txn_date (txn_date>? AND txn_date<?)']

Wrapping an indexed column in a function forces a full scan; comparing it directly to a range uses the index.

Do Do not
index columns used in frequent WHERE, JOIN and ORDER BY index every column
compare the column directly to a value or range wrap the column in a function in WHERE
check the plan after adding an index assume the index is used
Key takeaways
  • A table has rows (records) and columns (attributes); keys link tables, and you should verify a key is unique before joining.
  • Read a query top to bottom: SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT. WHERE filters rows, HAVING filters groups.
  • Join carefully: aggregate the many-side first, and compare row counts and totals before and after every join.
  • Use CASE WHEN for conditional counts, CTEs for multi-step logic and window functions for rankings, LAG and running totals.
  • NULL means unknown: use IS NULL, COALESCE and NULLIF, and remember COUNT(*) and COUNT(column) differ.
  • A default rate is only meaningful with an observation window; compare seasoned loans, not young ones.
